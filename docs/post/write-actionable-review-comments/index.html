검토 의견을 쓸 때, 문제와 제안을 한 문장에 섞지 마세요

막연한 평가 대신 위치, 이유, 원하는 변경을 구분해 검토 의견을 씁니다. 사실 확인과 취향 제안을 나누고 상대가 수정 여부를 판단할 수 있게 전달하는 방법입니다.

수정할 위치와 읽힌 내용을 적으세요 #

문서에 애매하다는 말만 남기면 작성자는 무엇을 고쳐야 할지 다시 물어야 합니다. 먼저 어떤 문단이나 항목을 읽고 의견을 남기는지 표시하세요. 그다음 현재 표현이 어떻게 이해되는지 설명합니다. 검토자의 해석을 적으면 작성 의도와 읽힌 내용 사이의 차이가 드러납니다. 상대의 능력이나 태도를 평가하는 말보다 실제 문장을 대상으로 이야기하는 편이 좋습니다.

예를 들어 신청 안내에서 대상과 조건이 같은 문장에 섞여 있다면, 어느 조건이 누구에게 적용되는지 구분하기 어렵다고 적을 수 있습니다. 가능하다면 해당 표현을 짧게 인용하되 문서 전체를 불필요하게 복사하지 않습니다. 여러 사람이 함께 검토하는 자료에서는 쪽번호만으로 위치를 지정하면 수정 뒤 달라질 수 있으므로 제목이나 항목명도 함께 남깁니다.

반드시 고칠 내용과 제안을 나누세요 #

수치가 원본과 다른 문제, 필수 조건이 빠진 문제, 표현 취향은 중요도가 다릅니다. 근거가 있는 오류는 확인할 자료와 함께 설명하고, 더 읽기 좋게 바꾸자는 의견은 제안으로 표시하세요. 모든 의견을 같은 강도로 쓰면 작성자가 무엇부터 반영해야 할지 판단하기 어렵습니다. 근거를 확인하지 못한 부분은 단정하지 말고 확인 요청으로 남깁니다.

검토 범위도 함께 정하면 좋습니다. 이번에는 내용 정확성만 보는지, 문장 표현과 형식까지 보는지에 따라 의견이 달라집니다. 이미 합의된 방향을 다시 바꾸려는 제안이라면 변경 이유와 영향을 설명해야 합니다. 검토자의 개인 선호가 조직의 공식 기준처럼 전달되지 않도록 실제 규칙과 제안을 구분해서 씁니다.

상대가 취할 행동을 분명히 하세요 #

문제를 설명한 뒤에는 원하는 결과를 적습니다. 두 조건을 문장으로 나누기, 근거 수치를 다시 확인하기, 선택 이유를 보충하기처럼 작업을 떠올릴 수 있는 표현이 좋습니다. 대체 문장을 제시할 수 있지만 그대로 사용해야 하는지 참고 예시인지 구분하세요. 작성자가 더 나은 해결책을 제안할 수 있도록 핵심 요구와 표현 선택을 나눕니다.

의견을 전달한 뒤에는 반영 여부와 남은 쟁점을 확인합니다. 수정했는지보다 처음 지적한 문제가 해결됐는지가 중요합니다. 반영하지 않은 의견은 이유를 남겨 다음 검토에서 같은 대화를 반복하지 않도록 합니다. 마감이 있는 자료라면 우선 처리할 항목과 나중에 보완할 항목을 함께 정해 검토가 끝없이 늘어나지 않게 합니다.
